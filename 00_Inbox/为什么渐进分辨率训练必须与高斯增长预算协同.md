### 3. 分辨率也参与本轮高斯增长率计算

```python
next_n_gaussian = int(
    (self.max_n_gaussian - self.init_n_gaussian)
    / cur_scale ** (2 - iteration / self.densify_until_iter)
) + self.init_n_gaussian

adjusted_max_rate = (
    self.max_densify_rate_per_step
    * cur_scale
    / self.max_reso_scale
)

return min(
    max((next_n_gaussian - cur_n_gaussian) / cur_n_gaussian, 0.),
    adjusted_max_rate,
)
```

## Codex 费曼追问

第一轮只回答一个问题：

> 假设训练前 5,000 次把图像宽高都缩小到四分之一，但高斯仍像全分辨率训练那样快速增长到 200 万。你认为像素计算、高斯参数优化、Gaussian–Tile 排序/光栅化这三类成本会分别发生什么？为什么这会造成“图像已经很粗，但场景表示却过度精细”的计算错配？

回答时不用讲 FFT 公式，也不用讲 CUDA kernel 实现；先把“像素量—高斯量—tile instance—可学频率”这条因果链讲清。

## 我的补充回答

第一轮回答：

> 即使图像的数量仅仅有1/16的像素分辨率，但是200万个高斯椭球也会针对已有的图片分辨率，来进行移动，分裂，投影，backward，更新的基数依旧没变，无非是在投影的时候的tile少了很多，但是依旧要把高斯球投影进去

判断：已经抓住主要的计算错配：像素和 tile 数量降低，并不会让高斯参数数量自动降低；大量高斯仍需参与参数处理、投影与可见性判断，产生 Gaussian–Tile instances，并承担反向和优化成本。需要修正的是 clone/split 只在满足增密条件和指定迭代间隔时发生，不是每轮让全部高斯分裂；此外 tile 数量减少也不保证 instance 数量按同样比例减少，因为大量高斯可能继续覆盖有限的 tile。

第二轮只追“监督信号与表示容量”的关系：

> 假设全分辨率图像中相邻的 4×4 像素包含窗框、墙面和细小纹理，但在 `render_scale=4` 时被缩成了同一个监督像素。此时即使安排许多不同高斯分别表示这些细节，loss 能不能告诉它们各自应该拟合窗框、墙面还是纹理？为什么？

第二轮回答：

> loss不能告诉它们应该各自去拟合什么细节，loss只会计算当前颜色和实际颜色之间的差距，最终只会去接近那个混合颜色

判断：正确。低分辨率监督只能约束下采样后的混合颜色，不能为已经合并的窗框、墙面和纹理分别提供可区分的高频误差信号；因此过早释放大量高斯容量缺少有效监督，也会浪费计算。

第三轮检查后期为什么必须反向释放容量：

> 当训练从 `render_scale=4` 升到全分辨率后，原来一个混合像素重新展开成包含边缘和纹理的 4×4 像素。如果高斯预算仍被永久限制在早期的较小数量，loss 虽然能看见这些新细节，模型为什么仍可能拟合不好？

第三轮回答：

> 高斯数量规模比较小的话，每个高斯的颜色和透明度有限，不够去拟合更加复杂的颜色

判断：方向正确，但当前解释把容量主要归因于颜色和透明度。更关键的是空间基元数量不足：一个高斯由 xyz、scale、rotation、opacity 和 SH 共同形成一个有空间范围的椭圆 footprint；当同一个高斯同时覆盖边缘两侧或多个不同细节时，仅调整一套参数难以让这些像素独立变化。

第四轮用具体边缘检验空间容量：

> 假设一个较大的高斯同时覆盖黑色窗框和白色墙面。为什么只调整这个高斯自己的颜色和透明度，很难同时把窗框像素变黑、墙面像素保持白？clone 或 split 出更多、更局部的高斯后，表达能力具体增加在哪里？

第四轮回答暴露出用户尚未稳定区分 SH 的视角变化、footprint 的空间权重和 opacity 的混合/遮挡作用。父问题暂停，先解决 [[一个 Gaussian 的 SH 与 opacity 能否在同一 footprint 内表达不同颜色]]。
